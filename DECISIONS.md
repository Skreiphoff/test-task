# Решения

## Приём вебхука

- **Подпись** проверяется middleware по сырому телу (`getContent()`), HMAC-SHA256 над `"{timestamp}.{body}"`,
  `hash_equals`, окно ±5 минут. Пустой секрет в конфиге — 500 (fail closed). Плохая подпись/timestamp — 401.
- **Невалидный payload** — 422 (после проверки подписи), включая несовпадение `X-Webhook-Id` и `id` в теле.
  Ретраи MarketHub для 4xx безвредны, но такой payload всё равно не заработает. Событие при 422 не сохраняется.
- **Идемпотентность** — по `id` события (первичный ключ `webhook_events`), не по подписи или времени, так как при
  ретрае они меняются. `INSERT ... ON CONFLICT DO NOTHING` внутри транзакции: параллельный дубль ждёт коммита первой
  транзакции и получает «0 вставленных строк». Дубль отвечает 200. Если первая попытка упала, откатывается и запись
  события, поэтому ретрай обработает его заново.
- **Состояние берём из снимка** `data.order`, а не из типа события. Неизвестный тип со снимком применяется,
  неизвестный тип без снимка сохраняется как `ignored`; оба случая — 200, чтобы не получить шторм ретраев.
- **Порядок доставки.** Побеждает снимок с большим `updated_at` (сравнение как моментов времени, не строк:
  смещения в примерах разные). Ранг статуса не используется, иначе нельзя было бы принять ручной откат статуса поддержкой.
  Внутри одной секунды (точность `updated_at` — секунда) снимок не может понизить статус. Заказ создаётся upsert-ом,
  поэтому `paid` до `created` не ломает обработку. Параллельное создание одного заказа решается `ON CONFLICT`.
- **История статусов** пишется только при реальной смене статуса. Для заказа, впервые увиденного в позднем статусе,
  добавляются записи, которые доказывает снимок (`created`, `paid` по `paid_at`). Время записи — `paid_at`/`cancelled_at`,
  а после отката (когда оно оказалось бы раньше последней записи) — `updated_at`.

## Письма

- Письмо ставится в очередь только при смене статуса на `paid`/`shipped`/`cancelled`, после коммита транзакции.
- Задание **перепроверяет состояние на момент отправки**: «оплачен» валидно в `paid/shipped/delivered`, «доставка» —
  в `shipped/delivered`, «отмена» — только в `cancelled`. Так отменённый заказ не получит «оплачен».
- «Не более одного письма каждого вида» гарантирует уникальный ключ `(order_id, kind)`: задание сначала занимает
  запись (`INSERT ... ON CONFLICT DO NOTHING`), потом шлёт. Если отправка упала, запись снимается и ретрай очереди отправит письмо.
- Фраза про возврат в письме об отмене — если у заказа есть `paid_at`.
- Письма простым текстом, тема — по `number`, а не по `id`.

## Данные

- Суммы — `decimal(12,2)` и строки в коде (без float), `subtotal` считается через `bcmul`.
- Времена хранятся как моменты времени (UTC, `timestamptz`) и отдаются в ISO 8601 со смещением `+00:00`.
  Контракт требует совпадения момента, а не исходного смещения, поэтому исходное смещение не сохраняется.
- Первичный ключ заказа — строковый id MarketHub.
- Невалидные параметры списка (`per_page=500`, неизвестный `status`) — 422, а не молчаливое исправление.

## Вопросы и принятые допущения

| Вопрос | Допущение |
| --- | --- |
| Что делать с письмами, если после отправки изменился `customer.email`? | Ничего не шлём повторно, письмо уходит на email из актуального снимка на момент отправки. |
| После отката `shipped -> paid` и повторной отправки нужно ли новое письмо? | Нет: письмо каждого вида уходит один раз за жизнь заказа. |
| Нужно ли письмо при `delivered`? | В задании его нет, не отправляем. |
| Заказ отменён после отправки — возврат применим? | Фраза про возврат зависит только от `paid_at`. Бизнес должен уточнить правила. |
| Приходит `paid` позже `shipped` (старее по `updated_at`)? | Считаем устаревшим: письмо «оплачен» не отправляем, история не дополняется. |
| Может ли `shipment` быть заполнен до `shipped`? | Отдаём как есть из снимка; `shipment` — `null`, если все три поля пусты. |
| Нужна ли строгая проверка email и валюты? | Нет, `currency` — 3 символа, email — строка; лишние отказы вызвали бы ретраи на 2 дня. |

## Что сделал бы дальше

- Админка сделана минимальной: серверные Blade-страницы без JS и сборки, только чтение, для ручной проверки.
  Использует тот же фильтр (`Order::scopeFiltered`), что и API. Полноценный UI (SPA, авторизация) — отдельная задача.
  Тестовые кнопки (`ADMIN_TEST_TOOLS`) подписывают событие секретом на сервере и прогоняют его через настоящий маршрут вебхука,
  а не пишут в БД напрямую, поэтому проверяют весь путь; по умолчанию выключены.
- Хранить сырое тело события (сейчас — разобранный JSON в `jsonb`) и чистить старые события по сроку.
- Метрики и алерты на `stale`, 401/422 и рост очереди; отдельная очередь для писем.
- Если нужно точное «момент оплаты» при потере `paid` до `shipped`, запрашивать актуальный заказ у MarketHub API.
- Тесты на настоящий параллелизм (несколько процессов) — сейчас гонка проверена вручную 18 параллельными запросами.
